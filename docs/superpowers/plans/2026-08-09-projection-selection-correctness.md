# Projection Selection Correctness Plan

**Date:** 2026-08-09

## Goal

Correct the two verified issues in the shipped TypeScript-inspired projection `pick(...)` / `omit(...)` feature without changing its intended semantics:

1. `@classification("level")` selectors currently match any classification annotation instead of the requested level.
2. `docs/language-reference.md` contradicts the implementation around combining selection clauses with projection body fields and includes an invalid `omit(...)` example that redeclares fields generated by the selection.

This is a correctness and documentation-alignment slice for shipped H1 behavior. It must not broaden the language surface.

## Current behavior

### Classification selector bug

`planner.py::annotation_matches()` correctly distinguishes annotation kinds but treats every `AnnClassification` value as equivalent:

```python
if isinstance(ann, AnnClassification) and isinstance(candidate, AnnClassification):
    return True
```

The IR preserves the requested level in `AnnClassification.level`, so selectors such as:

```mdl
omit(@classification("secret"))
```

must only match fields carrying exactly `@classification("secret")`.

The same matcher is shared by:

- `auto projections ... exclude [...]`
- projection `pick(...)`
- projection `omit(...)`

The fix therefore applies to all three surfaces and must remain centralized in the shared matcher.

### Documentation contradiction

The shipped implementation deliberately allows a selection clause together with additional projection body fields, for example:

```mdl
projection CustomerSummary @ 1
  from customer.Customer @ 2 as c
  pick(customerId, status)
{
  isActive = c.status == "active"
}
```

A body declaration is invalid only when its output name collides with a field generated by the selection clause.

The language reference currently says that mixing `pick`/`omit` with a projection body is a semantic error, which contradicts implementation and tests.

It also shows an `omit(...)` example that manually redeclares fields already generated by `omit`, which should trigger the existing selected/body collision diagnostic.

## Scope

### 1. Make classification matching value-sensitive

Update `cli/src/modelable/planner/planner.py::annotation_matches()` so:

- `@pii` continues to match by annotation kind.
- `@server` continues to match by annotation kind.
- `@classification("x")` matches only `@classification("x")`.
- different classification levels do not match.
- no separate matcher is introduced for auto projections or H1 selection clauses.

Expected rule:

```python
if isinstance(ann, AnnClassification) and isinstance(candidate, AnnClassification):
    return ann.level == candidate.level
```

### 2. Add regression coverage for classification values

Extend `cli/tests/test_projection_selection.py` with explicit multi-level fixtures.

Required cases:

- `pick(@classification("secret"))` selects only secret fields when secret and internal/confidential fields coexist.
- `omit(@classification("secret"))` removes only secret fields.
- a requested classification level with no matching field keeps the current unmatched-selector diagnostic behavior.

Also cover the shared matcher through auto projections so the fix cannot regress one surface independently:

- `reply exclude [@classification("secret")]` excludes only secret fields.

Prefer a direct shared-matcher unit test only if it improves failure locality; behavior-level tests remain mandatory.

### 3. Correct language-reference semantics

Update `docs/language-reference.md` section `3.5.1 Field selection: pick and omit`.

Replace the current body restriction with the actual rule:

- a selection clause may be combined with additional body fields;
- computed and explicit direct mappings are allowed;
- a body field may not reuse an output name generated by `pick`/`omit`;
- `pick` and `omit` remain mutually exclusive;
- `pick()` remains invalid.

### 4. Replace the invalid `omit(...)` example

Use an example where `omit(...)` produces the retained source fields and the body only adds genuinely additional fields, for example:

```mdl
projection CustomerWithoutSecrets @ 1
  from customer.Customer @ 2 as c
  omit(c.password, c.apiKey)
{
  displayName = c.legalName
}
```

The example must parse and validate under the real compiler.

### 5. Keep docs executable

The repository now treats grammar/docs drift as a correctness concern. Ensure the corrected examples are covered by the existing documentation example parse/validation tests where possible.

If the current docs test only parses fenced MDL and does not validate semantic collisions, extend the smallest appropriate test so this specific contradiction cannot return silently.

Do not create a parallel documentation-only parser or validator.

## Non-goals

Do not add or redesign:

- `Partial` / `Required`-style optionality transforms;
- mapped-type rename syntax such as `pick(c.customerId as id)`;
- projection union/intersection composition;
- structural auto-sync;
- new annotation kinds;
- general annotation-expression matching semantics.

Those remain separate language-evolution work.

## Implementation order

1. Add failing regression tests for classification value matching.
2. Fix `annotation_matches()` in the shared matcher.
3. Add/confirm auto-projection regression coverage.
4. Correct the `pick`/`omit` language-reference wording.
5. Replace the invalid `omit(...)` example.
6. Ensure documentation examples are exercised by the existing docs-as-tests pipeline.
7. Run focused and full validation gates.

## Acceptance criteria

- `@classification("secret")` never matches `internal`, `confidential`, `restricted`, or `open` fields.
- The same value-sensitive behavior is used by auto-projection exclusion and projection `pick`/`omit`.
- No duplicate classification matching logic exists.
- The language reference accurately documents that selection clauses may coexist with additional body fields.
- The language reference no longer contains an `omit(...)` example that redeclares generated fields.
- Corrected documentation examples parse and validate successfully.
- Existing H1 behavior, formatter round-tripping, dependency graphs, compatibility analysis, and canonical signatures remain unchanged.
- Full CLI regression suite and repository lint/type/documentation gates pass.

## Risk

Low and localized.

The code change tightens a shared annotation predicate to honor data already present in the IR. This changes current incorrect behavior for classification-based auto-projection exclusions and H1 selectors, so regression tests must cover all consumers of the matcher.

The documentation changes are descriptive only and should align prose/examples with behavior already enforced by the compiler.
