# Reference Implementation

Validates [spec.md](../spec.md) with Python, Pydantic, YAML, and pytest.

- Validate spec: `uv run python metamodel.py example.yaml [--stage inventory|discovery|architecture|verification|release]` (default `release`)
- Export schema: `uv run python metamodel.py --schema > schema.json` (committed; regenerate on model change, a test checks drift). Specs reference it via a `# yaml-language-server: $schema=…` modeline.
- Impact analysis: `uv run python metamodel.py example.yaml --impact order`
- Compatibility: `uv run python metamodel.py new.yaml --compat old.yaml`
- Context slice: `uv run python metamodel.py example.yaml --context checkout`
- Split specs: a root spec keeps `system` (plus `capabilities: []` and `components: []`) and lists `include: [spec/*.yaml]`; fragments hold any other section (schema: `fragment.schema.json`, `--fragment-schema`), are merged in sorted order, and the result is validated as one spec. Errors cite the fragment file. See `examples/components/`.
- Diagram: `uv run python metamodel.py example.yaml --diagram` — Mermaid flowchart (layers, nested domains, resolved capability dependencies, data ownership/lineage, status styling); renders natively on GitHub/Markdown
- JSON output: add `--json`
- Optional local artifact integrity: `--check-artifacts --root <repository>` checks declared source/schema paths and source/evidence SHA-256 hashes without executing or fetching artifacts. An explicit root is required; ordinary validation remains metadata-only.
- Delivery plan: `--plan <id>` prints provider-first waves of affected components (parallelizable within a wave) with each one's `requires`, `fakes`, `source_paths`, `test_paths`, plus requirements and evidence to revisit; built on `--impact`.
- Handoff scope: `--check-scope <component> --changed <file|-> [--allow <path>]...` reads changed paths (one per line, e.g. `git diff --name-only`) and reports any outside the component's `source_paths`, file `test_paths`, file `fakes` and owned `schema_path`s. Path comparison only; no filesystem access.
- Handoff return: `--check-return <file> [--allow <path>]...` checks an implementer's return (`component`, `results`, `unmet`, `changed`, `findings`; schema `handoff-return.schema.json`, `--return-schema`) against the spec: every active requirement targeting the component (or a capability it provides or data model it owns) is a result or unmet, result versions are current, passing results have no skipped checks, results may cover single criteria (`criteria`) and together must cover every criterion of a requirement unless it is listed unmet, test provenance is under `test_paths`, failing results are listed unmet, changed paths stay in scope. Findings are echoed in `--json` output.
- Cross-spec references: `system.imports` pins another system's spec (`path`, `version`, `capabilities: {id: version}`, optional `sha256`); an `external` component provides `<import-id>:<capability>` and consumers require it as `<import-id>:<capability>@^1.0`, so contracts are not copied (`IMP-01`). `--check-imports --root <repository>` loads each imported spec (path relative to this spec, inside the root) and verifies system version, pinned capability versions and `sha256`. Interfaces and data models of imported capabilities are not visible locally.
- Exporters: `--export backstage [--owner TEAM]` prints Backstage catalog entities (System, Component, API, Resource; multi-document YAML) and `--export structurizr` prints a Structurizr DSL workspace (components as containers, `external` ones as external software systems, resolved requirements as relationships). Backstage requires an owner that the metamodel does not model, hence `--owner` (default `unknown`). Lifecycle maps `verified`→`production`, `draft`/`specified`→`experimental`, `deprecated`→`deprecated`; API types are `openapi`/`asyncapi`/`other` from the interface. One-way, lossy exports; the spec stays the source of truth.
- Optional drift check: `--check-drift --root <repository>` parses Python sources and tests under `source_paths` and `test_paths` (never executes them), and scans JS/TS files (`.ts .tsx .js .jsx .mjs .cjs`) for `import`/`export … from`/`require()`/`import()` specifiers (regex over comment-stripped text; relative specifiers and workspace package names from `package.json` are followed, `node_modules` is skipped) and reports an import between components with no `requires` capability or `bindings` entry reaching the imported component, and JSON Schema top-level `properties` that differ from `DataModel.fields`. It also reads `Cargo.toml` manifests under `source_paths` (parse only): `path` dependencies (including `workspace = true` ones resolved from the root `[workspace.dependencies]`) that reach another component need a matching `requires`/`bindings` entry, and `dev-dependencies` on another component are rejected like test imports. Unsupported schema formats, test selectors, components without `source_paths`, external components' own sources and `via` edges are listed as `unchecked`. With `test_scope: integration`, test dependencies on providers of required capabilities are allowed.
- Run tests: `uv run pytest` (incl. `corpus.yaml`: one or more invalid patches of `example.yaml` per invariant ID; examples are the valid corpus)
- Docker: `docker build -t metamodel . && docker run --rm metamodel [python metamodel.py ... | pytest]`
- CI & remote: `.github/workflows/metamodel.yml` runs `pytest` automatically on `push`/`pull_request` and runs either script in Docker when dispatched manually (`script`, `args`)

Partial prototype; the serialization format is defined in [spec.md](../spec.md) (**Current reference format**).

## Validator Behavior

- **Schema**: unknown fields are rejected (`extra="forbid"`); `status` defaults to `draft`.
- **Invariants**: `INVARIANTS` maps each ID (spec.md § 11) to its stage, waiver kind and rule; errors are prefixed `[ID]`, and a test keeps the table in sync with spec.md.
- **Stages** (`--stage`): each invariant runs at its stage and later.
- **Waivers**: valid below `release` when `treatment` is `mitigation`/`acceptance`, `mitigated_by` is non-empty and `expires` (date or stage) is not passed (stage expiry: current stage after `expires`). `Risk.waives` accepts either the waiver kind or its invariant ID (`DATA-03`, `COMP-03`, `COMP-05`, `COMP-06`, `REQ-01`). Active waivers are listed as `waivers` in `--json` output.
- **Interfaces**: capabilities required by another component need `interface`; `operation`, `idempotent` and `auth` must be defined; `request`/`response` must name data models; `errors` keys must equal `failure_modes`.
- **Requirements**: `deprecated` requirements are inactive (no coverage, conflicts or evidence obligations); `Requirement.kind` must match its `category` (`REQ-07`); a conflict is resolved when either side's `resolved_by` names an active requirement; mandatory, mitigating, resolving and declassifying requirements need evidence and verified dependencies at `release`; `declassified_by` relaxes classification propagation only when it names an active requirement.
- **Component tests** (`COMP-08`): when a component declares `test_paths`, `test`-method evidence for it (subject is the component, a capability it provides, or a data model it owns) must have a `provenance` file part (before `::`) under one of them, or match a selector entry (`tool::selector`, exact or continued with `::`). Opt-in; components without `test_paths` are unchecked. `--check-drift` scans tests like source, and additionally rejects any test import of another component (declared or not): tests use the fakes.
- **Fakes** (`COMP-09`): a component that declares `test_paths` needs a `fakes` entry for each required capability, located under `test_paths` (file or selector), unless `test_scope: integration`; entries for capabilities it does not require are errors. `--check-artifacts` verifies the files exist. `COMP-10` (release): a capability that any component fakes needs an active `contract`-category requirement with valid evidence, so provider contract tests back the fake; fidelity of the fake to those tests is not checked.
- **Layers**: dependencies allowed within a layer or toward any lower layer (incl. non-adjacent); with non-empty `system.layers`, every component must declare one. Adjacency and source-code dependency rules need separate verification.
- **External components** (`COMP-11`): `external: true` declares no `layer`, `domain`, `requires`, `test_paths` or `fakes`, and is exempt from `COMP-02`, `COMP-03` and `DOM-01`; `--diagram` draws it as a hexagon outside the system listing its API. `via` maps a required capability to another required capability mediating it at runtime (`REF-05`); `--diagram` dashes such edges.
- **Domains**: optional and orthogonal to layers; with non-empty `system.domains`, every component must declare one (`DOM-01`). A dependency between components of different domains needs the target in the consumer domain's `uses` (`DOM-02`); `uses` is acyclic (`DOM-03`). Same-layer siblings that must stay independent are domains without `uses` between them. `--diagram` nests domain subgraphs inside layers.
- **Resolution**: excludes the consuming component; rejects ambiguous providers without a binding, dependency cycles, and active components requiring deprecated capabilities (`COMP-07`); one version per capability ID.
- **Versions** (`_ver_ok`): dot-separated integers; equal major, remaining segments ≥ minimum; non-numeric never matches. No segment normalization, major-zero rules, prereleases or general ranges.
- **Risks**: mitigating requirements need valid evidence; `avoidance` also needs verified `mitigated_by` and no `residual_accepted`; `acceptance` and `transfer` need `residual_accepted: true`, and `transfer` needs `transferred_to`. Accepted residual risks are listed as `residual_risks` in `--json` output. Mitigation effectiveness is not checked.
- **Classification**: missing classification is `unknown`; inventory requires an active `classification_review` requirement. Unknown classifications block architecture and later stages, including when lineage is declassified (`DATA-05`, `DATA-06`). Existing inputs that omitted classification must now state a reviewed value or an inventory review obligation.
- **Evidence**: requires a passing, unskipped record for `(requirement_id, requirement_version)`; rejects unsuperseded failures. `model-check` requires `bounds`; `subject_id` must resolve. At release, `timestamp` and `verifier` are required. Explicit `subject_version` / `subject_revision` pairs match `subject_bindings` and current modeled versions (`EV-04`); legacy version-valued `subject_revision` remains supported when no binding/pair is declared. Skips block release (`EV-05`). Optional `artifacts` hashes verify local file integrity only; criterion coverage, Git authenticity and build correspondence remain review obligations.
- **Evidence criteria** (`EV-06`, `REQ-04`/`REQ-05`): `Evidence.criteria` lists the requirement criteria a record covers (exact strings; empty = whole requirement). Per-test or per-group records can then verify a requirement criterion by criterion: it is verified only when every non-superseded record passes and every criterion is covered by a passing record (or one whole-requirement record). `REQ-04`/`REQ-05` name the failing or uncovered criteria. A failing criterion still blocks release; criteria make it attributable, not waivable.
- **Compatibility** (`check_compatibility`, `check_data_compatibility`, `--compat`): compares clauses as string sets; reports added preconditions, removed postconditions/invariants, added failure modes, capabilities removed without prior `status: deprecated`, removed data models, data models with removed fields, changed field types or classification, and missing major bumps. No clause semantics, interface or constraint comparison.
- **Context** (`--context`): the component, its provided/required capabilities, owned and interface data models, applicable source bindings, and requirements/risks targeting them or the system; evidence excluded.
- **Impact** (`impact_analysis`, `--impact`): follows capability, ownership and lineage dependencies transitively; reports affected components, capabilities, data models, requirements (incl. system-level and dependent) and evidence (by requirement or `subject_id`). Stored evidence is not changed.

## Limitations

- `consistency` and `quality_attributes` parsed only. Source/schema paths are checked for existence/containment with `--check-artifacts`; `--check-drift` covers Python imports, JS/TS relative and workspace-package imports (not tsconfig `paths` aliases, bundler aliases or computed specifiers), Cargo `path`/`workspace` dependencies and JSON Schema property names only (no other languages or formats, registry or `target.*` Cargo dependencies, field types, `required`, `$ref`/`$defs`).
- Schema additions are backward compatible for specs (new fields are optional) but not forward compatible for tools: a validator older than a field rejects specs that use it (`extra="forbid"`), e.g. `test_paths` requires a validator that includes it.
- No automatic evidence invalidation; impact analysis only reports it.
- Results separate schema from metadata errors; metadata errors carry invariant IDs but not stage labels.
- JSON Schema does not encode all invariants.
- Example test and benchmark provenance values are illustrative; sample formal models are supplied in [`../examples/greenfield/Inventory.tla`](../examples/greenfield/Inventory.tla), [`Inventory.cfg`](../examples/greenfield/Inventory.cfg), [`Inventory.als`](../examples/greenfield/Inventory.als) and [`metamodel.als`](metamodel.als).
- `VALID` means only that implemented checks found no errors; passing tests establish only the behavior they cover.
